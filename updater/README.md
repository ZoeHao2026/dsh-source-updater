# Local DeepSeek Harness source updater

This helper checks official published `dsh-v*` GitHub releases, including alpha, beta and rc versions. It compares full SemVer versions, resolves annotated tags to immutable commits and builds a local unsigned Windows x64 installer. It never invokes Codex, another agent or an automatic source repair service.

An unavailable release query records `check-unavailable`; it changes neither the installed program nor its qualification and permits another explicit client launch to check again. Native observers keep this network failure quiet and do not schedule polling retries. `status` reports a live worker lock as `busy` even before its owner has published its next phase, so check and preparation observers join the same task. Only a qualified explicit manual retry can discard a stale candidate whose pinned source patch or active plugin selection changed; the old build remains preserved.

`upgrade-worker.mjs check|prepare|preflight|apply|status --config <absolute updater-config.json>` writes one JSON result to stdout. Check accepts `--request '{"currentVersion":"0.2.1-alpha.5"}'`. Prepare accepts a schema 1 request with `target:{version,tag,commit}`. Preflight requires target, currentVersion, original appPid and fixed installDir/userDataDir/sharedDataDir; it verifies current state while Host remains running, without admission or installation. Apply requires the same fields plus a native admission attestation. All activity counters must be exactly zero, drafts saved, requests drained and input idle for 60 seconds. Paths must equal the installed configuration.

Current Desktop dependency declarations, selected bundles, runtime bytes and cached plugin fingerprints must match the qualified baseline. Removed or newly added plugins block installation; the helper never reinstalls a removed plugin to satisfy its baseline. Modified manifests or adapted presets require an explicit absolute `activePluginPins` path to a trusted qualification manifest with `plugins:[{name,version,files:{relativePath:sha256}}]`. Never generate this trust record automatically from unreviewed active files. Old ready records without a plugin fingerprint require fresh compatibility qualification.

`config.plugins` is the explicit, reviewed, nonempty selection of frozen local baselines. It can contain only the model-selector plugin when the user has removed the optional modes. Empty selections, duplicate names, undeclared packages and mismatched bundle selections fail closed. The worker passes these exact names as `selectedPlugins` to the compatibility probe and accepts only the same exact name set in its result. It never infers a new trusted selection from a changed live profile. Preparing a different selection uses a separate source cache; an old three-plugin ready record cannot qualify a one-plugin profile.

Successful updates advance an existing explicit trust record from the verified candidate hashes after the final health check against the promoted real data. The exact CLI configuration file and its distinct `activePluginPins` file must be physical files inside the helper root. Their original bytes and hashes join the transaction backup; the journal records both planned values before either atomic rename. The helper verifies promoted plugin bytes against the candidate, commits the new pins and actual `currentVersion`, then completes the transaction. It does not create a new trust record when none was explicitly configured. Known failures restore these helper files together with the old program and data; external helper edits, corrupted backups, uncertain child outcomes and failed recovery writes retain the lock and recovery evidence. Native requests use their actual running version, and standalone checks fall back to the transactionally maintained configuration version.

Failed native handoff stops automatic switching of that candidate until an explicit retry. Later ordinary launches still check for a different published target, without repeating the rejected switch. Per-request private logs preserve the worker's rejection, and acceptance binds the token and spawned worker PID. A still-running helper without verified acceptance or failed Host recovery requires local inspection; retry cannot override that uncertainty. Preparation, deterministic preinstall and rollback failures quarantine the candidate across future launches; `manualRetry:true` in an explicit check/prepare request can clear the rejection only after current qualification succeeds. It cannot clear a recovery lock.

The native shell performs launch and second-instance checks in the background, coalesces concurrent requests, acquires the runtime task lock, flushes drafts, drains requests, gracefully stops its backend and exits before the detached apply worker proceeds. A live worker lock returns `busy`; native callers poll status and join the same task. Complete ownership bytes are atomically published by an exclusive hard link inside the physical helper directory; a normally disappearing lock causes status to reread the completed task. A dead or malformed lock is retained for local inspection. Safe retry preserves failed build directories and starts another build; uncertain process termination never silently retries or steals a lock.

Checks and source preparation run in detached independent Node processes with per-request file-backed output, so ordinary client exit does not terminate their Windows process jobs or close a required output pipe. A restarted client joins the existing lock and reads durable status. A completed observer removes only its own output files; output from a client that exited remains private evidence in the helper directory. Installation continues to require its separate accepted handoff and the original application PID to exit.

Prepare verifies the pinned baseline plugins, the official published tag and source commit, applies the exact saved compatibility patch, enforces the source's pinned pnpm version, uses `pnpm install --frozen-lockfile`, runs unsigned packaging preflight and the complete official packaging command, then runs the fixed plugin compatibility probe. The assembled application's official integrity and runtime smoke checks are part of packaging. A patch conflict or plugin failure blocks promotion and preserves the running application.

Windows source builds use a separate persistent `buildCacheDir`, defaulting to `Documents\DSHB` under the current account. This must be an owned local physical directory of at most 64 characters, outside the helper, client installation and user data roots. The worker rejects reparse points, redirection to a different or longer physical path, another updater's marker and any unfamiliar nonempty cache. It retains failed trees and never changes Windows long-path policy. A 16-character commit/tag/patch/qualified-selection digest identifies each build; source lives in its `s` child. Git long paths are enabled only in that checkout. Installation adds `--config.virtual-store-dir-max-length=40`, so pnpm's dependency patching avoids the previously redirected long `process.chdir` path. Frozen lockfile, full builds, fixed source patch and plugin checks still apply. Status and ready records retain explicit sourcePath; older records with a source child remain readable. Deploy options may set buildCacheDir explicitly; dry-run reports it without creating it.

Apply checks the original PID has exited and inspects Windows process metadata for competing writers. It snapshots the whole installation, shared Harness home and Electron userData with hashes. Junction targets are materialized in backup data and original topology is recorded. Cycles, concurrent changes and special files fail. Links into Electron's app.asar remain opaque placeholders in isolated copies, with original link metadata retained and the entire archive backed up as program data. Restoring external targets that changed concurrently blocks instead of overwriting another project.

A confirmed competing writer after native exit quarantines that candidate before installation and leaves the original program and data intact. The helper does not restart another Host while a writer is present. End the competing writer, reopen the client and explicitly retry the update after inspection; ordinary cold launches cannot repeat that candidate's automatic shutdown. If this rejection cannot be saved, the helper retains its lock and reports recovery-required. Unknown application exit or process-inspection deadlines retain their existing inspection barriers.

After the original process has definitely exited and writer inspection passed, failure to create the private transaction directory or its initial journal also quarantines the untouched candidate. Partial transaction directories remain available, the original program and data remain intact, and retry requires inspection and an explicit user action. Failure to save this rejection retains the recovery lock; it does not turn an unknown original-process exit into a retryable failure.

Completed backups recheck the source child inventories, file hashes and link topology before migration and installation. A file changed after its earlier copy therefore invalidates the backup. This detects observed concurrent changes; it does not grant exclusive access against unrelated processes that ignore application ownership. History-probe JSON is parsed and validated before installation. Health qualification requires both a valid receipt and a successful child exit; a nonzero exit cannot be hidden by an earlier receipt.

Retired dependency trees retain their original pointers without recursively copying unrelated source repositories. Active Desktop dependencies remain materialized. Dangling links are recorded with their Windows link type and retained as placeholders during qualification; promotion and rollback restore their original topology. Existing per-user installation registry entries and shortcuts are also backed up. Successful installation restores original shortcut bytes, and rollback restores installation metadata with the matched application and data.

Migration runs against materialized snapshots, with compatible plugin archives installed into the isolated profile. The native health mode disables schedules before profile startup, blocks user admissions, returns a token-bound receipt after actual plugin/profile checks, and exits only when the helper writes its release marker. The helper validates the unpacked application, reads history with the target persistence backend, hashes attachments, installs `/S /D=<same installation directory>`, validates the installed application against the isolated state, promotes the migrated data and performs a final health run against the real paths before launching normally. Failed deterministic installed checks restore matched program, data and settings snapshots; uncertain process outcomes preserve locks and journals for recovery. Preinstall failures restart the intact old client only after confirming no competing writers. Backups and displaced failed trees remain available.

History acceptance compares both runtimes against isolated copies. Every session readable by the old runtime must remain readable. An old unreadable record may only remain unreadable when its exact error is unchanged and every original raw generation still matches its saved digest. These records are reported separately, never counted as readable. Readability baselines are cached only under the complete old program digest and raw session inventory digest. Named images and files are read through the target attachment provider, in addition to hashing the complete attachment tree.

Deployment is reversible helper-file creation only: `node deploy-updater.mjs --options <absolute JSON> [--dry-run]`. Options include destination, sourceRepository, pluginAssets, nodeExecutable, pnpmDirectory, npmDirectory, gitExecutable, powershellExecutable, installDir, userDataDir, sharedDataDir and optional currentVersion/compatibilityPatch/buildCacheDir. It copies standalone Node, pinned pnpm and npm CLI, fixed probe assets and immutable baseline plugin copies, then writes updater-config.json. Missing compatibility patches remain fail-closed. Deployment does not stop or modify the client or shared data.

Set options.destination to the current user's physical `Documents\DSHUpdater` directory, for example `C:\Users\YOURNAME\Documents\DSHUpdater`. This contains the permanent helper, tools, frozen plugin baselines and updater-config.json. Keep options.buildCacheDir separate: `Documents\DSHB` holds disposable source builds and must not contain the helper or user data. Desktop discovers an explicit `DSH_SOURCE_UPDATER_CONFIG` first, then `DSHUpdater` under the Windows Documents directory, then the legacy `%LOCALAPPDATA%\DSH Source Updater` directory. An explicit configuration path does not fall back when missing. If a different permanent destination is required, set DSH_SOURCE_UPDATER_CONFIG to its absolute updater-config.json path in the launching environment. AppData can be virtualized when deployment runs inside an MSIX application, so verify the Documents helper and configured root are visible from an ordinary Explorer-launched process. Health child processes receive the selected configuration explicitly. Do not replace helper files or configuration while its worker lock is held.

For the extracted source-updater kit, set options.pluginAssets to the absolute extracted `plugins` directory. Its `baseline-pins.json` uses relative `baseline-sources/dsh-*` directories and lists the original 77 hashed files across all three plugins. Relative paths and their physical files must stay inside pluginAssets; traversal and junction escapes are rejected. Existing local manifests with absolute plugin paths remain supported for prior deployment options. The helper copies only pinned files into its saved probe packages and immutable baseline. The public source release contains helper source, patches, plugin baselines and summarized verification scope; it does not contain a complete Node/pnpm/npm runtime or the full official Harness checkout. Node 24+, the complete pinned pnpm 11.28.5 directory, npm CLI, Git, PowerShell, sourceRepository and the existing installation/data paths must still be supplied by the target machine. Future source builds fetch the approved published tag through the existing checks.

`node --test deploy-updater.test.mjs` checks extracted relative pins against all 77 file hashes, traversal and junction rejection, legacy absolute-path compatibility, exact-inventory copying and a deployment dry-run that creates no helper directory.

Plugin tools also require explicit local inputs. Run `node ../plugins/probe.mjs --source <absolute official checkout> --config <absolute JSON>`; set that JSON's outputDir (or pluginOutputDir) to a separate absolute scratch directory, and optionally expectedCommit/npmCli. Its optional `selectedPlugins` is an explicit nonempty list of known names without duplicates; omitting it retains the original three-plugin probe for source-kit compatibility. Only the selected contracts and packages are qualified. The probe uses deployed packages first, falling back to public baseline-sources only when packages is absent; config.baselineRoot can select an explicit absolute baseline directory. Run `node ../plugins/typecheck-target.mjs --source <absolute built official checkout>` to check all 11 model-selector TypeScript source files against that checkout's built public declarations, installed TypeScript and dependencies. An optional `--plugin-root <absolute UI plugin directory>` checks another materialized copy. Neither tool discovers a live profile or assumes an adjacent official checkout. The static probe and type check do not establish native plugin UI acceptance.

The optional `node test-short-pnpm-build.mjs --source-checkout <absolute official checkout>` fixture requires a separately supplied official checkout with pnpm 11.28.5 installed and npm CLI beside the selected Node executable. It rejects missing arguments before creating its temporary directory. It packs one local fixture and performs a real offline, frozen patched-dependency installation in a temporary short owned cache, checks patched bytes, a 40-character virtual-store folder and an unchanged lockfile, then removes only its temporary fixture. Its JSON result remains under tests. It does not build an official release, deploy the helper or access live Harness data.

From this updater directory, run `node --test upgrade-worker.test.mjs baseline-compatibility.test.mjs preflight.test.mjs qualification.test.mjs deploy-updater.test.mjs` with Node 24+ on Windows. They use the public pinned plugin files and temporary fixtures; they require no deployed updater configuration, live Harness data or official source checkout. They cover explicit one-plugin qualification, cache separation, duplicate/empty/extra selections, trusted-pin progression, partial helper commits and preservation of external edits. The deployment dry-run uses a fake pnpm manifest and absolute tool placeholders, and executes only the selected Node executable to read its version.

The recovery integration fixture is a separate explicit opt-in: first create inputs with `node recovery-integration.mjs --create-fixture-inputs <absolute empty owned sandbox>`, then run `node recovery-integration.mjs --fixture-config <absolute fixture JSON> --compatible-manifest <absolute compatible plugin manifest JSON> --workspace <absolute owned disposable sandbox>`. Optional single fault modes are `--writer-blocks-rollback`, `--journal-failure`, `--invalid-data-probe`, `--health-nonzero`, `--qualification-success`, `--qualification-partial-failure` and `--qualification-journal-failure`. All three run paths are mandatory before any configuration is read or temporary root is created. The workspace must already exist, be physical and be owned by the current Windows account; fixture roots and reports are written inside it. Only the generated fixture configuration and synthetic plugin manifests are accepted; production configuration is forbidden. The fixture drives the real apply coordinator with disposable program/data/settings roots and fixture installation metadata. The qualification modes validate successful pin/version advancement, exact matched rollback after pins have committed but before config has committed, and lock retention when the journal becomes unwritable at that boundary. Partial-commit faults are inserted only into a disposable worker copy. This does not establish live NSIS fault recovery or real registry restoration.

`test-data-probe.mjs` is not part of the standalone command: it requires separately prepared runtime/source inputs. Full initial installation qualification must separately record actual packaging output, native health receipts, plugin UI interactions and rollback evidence. Process inspection is conservative but is not an OS-level cross-application write lease; another unrelated process can still modify shared files after inspection. Failed or uncertain backup consistency prevents installation.
