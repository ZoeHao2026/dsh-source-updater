# Deploying and maintaining the source updater

`node deploy-updater.mjs --options ABSOLUTE_JSON --dry-run` validates the reviewed delivery and prints its plan without creating a helper, build cache or trust file. It reads tool directory inventories, but does not hash every installed Node/npm file during the dry run. A real deployment verifies managed destination bytes before writing them and records the copied delivery hashes in `deployment.json`. Configuration, trusted plugin pins, status and transaction records remain mutable state outside that inventory.

The options JSON uses the absolute paths listed in `README.md`. Optional `selectedPlugins` is an explicit nonempty list of distinct plugin names present in the reviewed `baseline-pins.json`. Omit it on a first deployment to retain the source kit's original three-plugin selection, or specify only `@local/dsh-ui-model-selection-collapsible` for a reviewed model-selector-only deployment. The deployer never examines the live profile to invent a selection or qualification, and never installs a plugin into live user data.

Each first deployment writes an explicit helper-local `trusted-active-plugins.json` from the verified frozen baseline manifests and file hashes. These initial pins qualify the frozen versions only; an already adapted live plugin still requires its separately reviewed qualification. After successful update health checks, the worker advances this configured trust record from the exact verified candidate hashes, together with the installed version. This permits later updates without trusting arbitrary live edits.

An existing deployment must identify the same physical helper directory, configuration path and client/data paths and must have a delivered-file ownership inventory. Its existing explicit plugin selection is preserved when `selectedPlugins` is omitted. Its trusted pins are preserved byte-for-byte when the selection is unchanged, including pins advanced by a successful update; redeployment also preserves the transactionally maintained current version. An explicit changed selection preserves qualification for retained plugins and uses frozen baseline pins for newly selected ones. Removed plugins are excluded from the helper configuration; no plugin is reinstalled into user data. Unrelated files are never adopted as owned, changed managed files are retained with an error, and a worker lock prevents concurrent deployment.

Unrecognized nonempty directories and legacy deployments without a delivered-file ownership inventory are refused without changes. To upgrade such a helper, keep its original directory and backups, deploy the reviewed kit to a new empty physical directory using explicit client/data/tool paths and an explicit `selectedPlugins` selection, review the generated baseline pins against the actual installed plugin qualification, then set the client's `DSH_SOURCE_UPDATER_CONFIG` environment variable to the new absolute `updater-config.json` path and reopen the client. This explicit override takes precedence over the default Documents helper. Do not synthesize trusted pins from unreviewed live files; adapted plugins need reviewed candidate hashes. If the new helper is not usable, restore the previous environment-variable value and reopen the client; both helper directories remain intact. `--dry-run` can inspect both plans before deployment. This deployer never replaces the client or promotes data; the separately backed-up maintenance deployment used for the current production installation is a different procedure.

Before changing files on a recognized redeployment, its prior configuration, pins and deployment record are copied to a new `deployment-history` subdirectory. A failed or interrupted helper-file copy is not claimed as a completed deployment; retain that directory for inspection. Program and data updates, their snapshots and rollback remain owned by the worker's update transaction.
